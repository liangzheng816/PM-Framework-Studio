capabilities

Five things it does

Every Review, Critique, and Draft is calibrated against how the indexed corpus actually reads today — and grounded by the two search tools.

01

Review

A final Learn content-reviewer pass — findings ordered Must Fix → Should Fix → Polish, calibrated to the active doc-set's corpus. Catches an unstated role, a governance feature missing its license, “by default” with no change path, a stale admin-center path, or PowerShell missing Connect-SPOService. Optional rewrite at the end.

02

Critique

An adversarial pre-publication gate: a 7-dimension scorecard, reader-modeled gap questions, named failure modes, a logical-consistency and cross-corpus check, and an explicit ✅/⚠️/❌ verdict with the top-3 fixes. It never flatters, never rewrites, and never softens a 2/5.

03

Draft

Turn a PM spec, feature notes, or admin steps into a new Learn article in corpus-standard structure — frontmatter (and an applies-to banner for Server), reused canonical hub links, [TBD: …] markers, and a Needs confirmation section for every fact it can't verify.

04

Find similar

Ranked corpus articles with title, an overall summary, ms.topic, audience, ms.date, the learn.microsoft.com URL, local path, matched terms, and a snippet. Scope to the active doc-set, or span cloud, on-prem, and dev at once with --all-docsets.

05

Find Doc

An exact lookup — resolve a Learn URL (or slug) to its precise local .md file, with doc-set, id, title, ms.topic, audience, and a short summary. Index-first, with a filesystem fallback for brand-new files and closest-slug suggestions when nothing resolves.

+

Refresh corpus

One command re-indexes DocRepo + DevDocRepo across all doc-sets and regenerates the corpus-derived pattern files — then verifies parity.

Strict isolation. Cloud uses the SharePoint admin center, tenant, and *-SPO* cmdlets. On-prem uses Central Administration, farm, content database, *-SP* cmdlets, and PSConfig. Developer uses SPFx / PnP / REST / CSOM / Graph. sharepoint-dev comes from the separate sp-dev-docs repo.

Multi-doc-set by design. Each doc-set carries its own corpus, references, terminology, and learn_base_url. Add another product area or locale by adding a key to config/docsets.json and a terminology file, then re-indexing — no code changes.

workflows

From a single chat prompt

Before any Review, Critique, or Draft, the agent locks the active doc-set. Cross-doc-set work is search-only via --all-docsets.

1

Review an article

Reads the doc-set's checklist + best-practices, searches the corpus for calibration, identifies the ms.topic shape, and returns Must / Should / Polish findings.

2

Critique (adversarial)

The toughest read before a PR. Scorecard, gap questions, failure modes, logical-consistency + cross-corpus checks, an explicit verdict, and the top-3 fixes. No flattery.

3

Critique as a persona

Voice the critique as the tenant admin, farm admin, technical editor, content PM, support engineer, or accessibility reviewer — or a real colleague's curated profile.

4

Draft a new article

Picks the closest template, reuses the corpus's canonical links, and writes in Learn style with frontmatter — flagging every missing fact as [TBD].

5

Find similar / Find Doc

Fuzzy topic search scoped to one doc-set (or all), and an exact URL→local-file resolver with a short summary so you can confirm the article without opening it.

6

Refresh the corpus

distill_new_knowledge.py rebuilds the indexes, regenerates the pattern files, and verifies parity in one shot — re-run after a git pull.

scoring

Seven dimensions, scored 0–5

Critique scores each article on seven dimensions; personas re-weight them. Each doc-set's terminology and corpus patterns define what "correct" means.

01

Technical accuracy

UI paths, cmdlets, roles, licenses, versions, limits, defaults — correct, not invented.

02

Completeness

Every decision point, default, option, and limitation the reader needs is present or linked.

03

Task-orientation

A reader can actually complete the task from the steps as written, in order.

04

Prerequisites & setup

Required role, license/version, module, and account stated before the first step.

05

Metadata & frontmatter

title, ms.topic, ms.date, audience, customer-intent — and the Server applies-to banner.

06

Terminology

Canonical names used consistently per the doc-set; "Select", not "click"; no cross-world terms.

07

Findability & structure

One H1, no skipped levels, descriptive headings, coherent outline, next steps.

∑

Verdict

All seven ≥ 4, no Risk-grade failure mode, no logical inconsistency → ready.

✅ Ready to publish ⚠️ Needs revision ❌ Not ready

Under an admin persona the bar is stricter: any single heavily weighted dimension — Technical accuracy, Task-orientation, or Prerequisites — scoring low solo-fails the verdict, however polished the rest is. A doc a real admin can't safely follow isn't ready.
